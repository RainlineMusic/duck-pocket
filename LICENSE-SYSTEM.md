# Duck Pocket: device-bound activation v2

## Пользовательский сценарий

В окне активации два режима: **Online (Recommended)** и **Offline**.

Online: покупатель вводит короткий ключ `DUCK-7K3M-9X2P-6R8N-4W5T`.
Плагин по HTTPS запрашивает подписанную лицензию для текущего устройства,
проверяет подпись и привязку, затем сохраняет её локально. Интернет нужен
для первой Online-активации. При создании экземпляра и открытии редактора
плагин делает одну фоновую проверку сохранённой лицензии. Недоступность сети
не прерывает работу; периодических повторов и запросов при Play нет.

Offline: редактор показывает числовой код устройства и кнопку Copy code.
Покупатель получает файл `.ducklicense` в разделе Devices личного кабинета
https://rainlinemusic.su/account по коду устройства. Offline занимает один
из общего лимита в три устройства, как и Online. Покупатель
перетаскивает файл в окно Offline или нажимает Choose file. Готовый
универсальный файл после покупки не рассылается.

Оба режима сохраняют одну и ту же подписанную лицензию. Активация общая для
экземпляров и форматов VST3/AAX/AU/CLAP у текущего пользователя ОС. Другой
пользователь ОС может импортировать тот же файл на том же компьютере.
На другом компьютере этот файл не активирует плагин.

Без лицензии звук проходит dry с объявленной задержкой; ducking, Output Gain,
прослушивание sidechain и звук логотипа отключены. В аудиопотоке только
atomic<bool>, без сети, диска, системных идентификаторов или RSA.

## Код устройства

Используется JUCE **8.0.4** `SystemStats::getUniqueDeviceID()`:
macOS — IOPlatformUUID; Windows — идентификатор из SMBIOS. Не MAC/IP/имя пользователя.
Возможна смена ID при замене оборудования/прошивки/клонировании виртуальной
машины. Абсолютная уникальность системных ID не гарантируется. Пустой или
очевидно нулевой ID не заменяется общим значением: активация завершается ошибкой.
Новый ID требует нового файла. Обновление JUCE нельзя делать без теста
стабильности ID между выпусками.

ID вычисляется один раз на создание общего LicenseState, не каждый кадр/аудиоблок.
Исходный ID нигде не сохраняется и не отправляется серверу.

Точный алгоритм (ASCII):

1. `id = trim(systemID).lowercase()`.
2. `platform = "mac"` или `"win"` ("other" только для локальных тестов).
3. `H = SHA256("DuckPocket|device|2|" + platform + "|" + id)`.
4. `N = big_endian_integer(H[0:16])` (128 бит).
5. `body = "2" + decimal(N).leftPad("0",39)` (40 цифр).
6. `check = big_endian_integer(SHA256(body)[0:2]) % 97`.
7. `device = body + decimal(check).leftPad("0",2)` — 42 цифры.

UI группирует код по 6 цифр, 7 групп. Генератор принимает дефисы и пробелы,
проверяет длину, диапазон N и checksum. Checksum помогает найти опечатку,
а защиту обеспечивает подпись. Хеш — псевдоним устройства, не обещание анонимности.

## Подписанный файл DP2

Файл: одна ASCII-строка, необязательный завершающий перевод строки. Не JSON,
не исполняемый код. Импорт ограничен 1 KB, максимальный ответ API — 8 KB.

`DP2.<uuid>.<device42>.<signature512hex>` — ровно 596 символов.

- UUID: 36 символов, нижний регистр, канонические дефисы.
- Подписываемое сообщение `M = ASCII("DuckPocket|2|" + uuid + "|" + device42)`.
- RSA-2048, e=65537, RSASSA-PKCS1-v1_5, SHA-256.
- `T = hex(3031300d060960864801650304020105000420) || SHA256(M)`.
- `EM = 00 || 01 || FF × 202 || 00 || T`, 256 байт.
- `s = OS2IP(EM)^d mod n`, подпись — lowercase hex(I2OSP(s,256)).
- Плагин проверяет полный padding/DigestInfo, `0 < s < n`, затем `s^e mod n == EM`.
- Device из файла должен точно совпасть с текущим кодом устройства.

Публичный n — Source/LicensePublicKey.h. Секретный PEM прежний; он не попадает
в плагин, репозиторий, браузер, ответы API или CI-артефакты.
**Универсальные DP1 из предыдущего прототипа больше не принимаются.**
Иначе прежний ключ позволил бы обойти привязку. Старый файл не удаляется,
но нужен новый DP2 для устройства. Состояние DAW не активирует плагин.

Лицензия хранится в userApplicationDataDirectory/RainlineMusic/DuckPocket/license.key:
macOS `~/Library/RainlineMusic/DuckPocket/license.key`, Windows
`%APPDATA%\\RainlineMusic\\DuckPocket\\license.key`.
Запись через TemporaryFile + атомарную замену, только после проверки.
Некорректный файл не заменяет уже действующую лицензию.
Другие процессы/форматы видят изменение через 2 секунды при работающем
message loop. RSA повторяется при изменении файла/отметки отзыва, импорте и перед запросом
проверки; в аудиопотоке и покадровой отрисовке RSA нет.

## Ручная выдача Offline

На компьютере продавца: Python 3 и `pip install cryptography`.

```sh
python Tools/licensing/generate_license.py --private-key /private/duck-pocket-signing.pem --device-code "КОД_ИЗ_ПИСЬМА" --license-id "UUID_ПОКУПКИ" --output DuckPocket-License.ducklicense
```

Если UUID ещё нет, можно опустить --license-id: создастся случайный UUID.
Сохранить UUID/файл за покупкой. Для повторной выдачи/другого устройства
использовать тот же UUID; код устройства меняется. Отправлять только
`.ducklicense`, никогда PEM. Наличие кода устройства само по себе не
доказывает покупку: продавец отдельно проверяет заказ.

PHP на сервере:

```php
require 'generate_license.php';
$file = duckPocketLicense($privatePem, $purchaseUuid, $deviceCode);
```

Нужны PHP OpenSSL и RSA-2048 PEM. Python и PHP используют один формат.

## Подключение Online к сайту

Рабочий endpoint: `https://rainlinemusic.su/api/v1/activate`.
Он задан по умолчанию в CMake и GitHub Actions. Repository variable
`DUCK_LICENSE_API_URL` позволяет заменить адрес при необходимости.
Сайт должен быть обновлён до версии, поддерживающей device42 и точный формат DP2 ниже.

Задать CMake `-DDUCK_LICENSE_API_URL=https://your-domain.example/api/duck/activate`.
В GitHub Actions — repository variable `DUCK_LICENSE_API_URL`; workflow
передаёт её в Mac/Windows CMake. После изменения URL требуется новая сборка.
Только HTTPS, без редиректов; TLS проверяет системный сетевой backend JUCE.
Запрос запускается по нажатию OK в отдельном отменяемом потоке. На аудио/UI
нет ожидания сети; worker принадлежит процессору, а не окну. Закрытие редактора
не оставляет callbacks на уничтоженные компоненты. При уничтожении последнего
процессора запрос отменяется, поток присоединяется до выгрузки модуля.
Сетевой timeout 8 s; максимум 8 KB ответа. Реальные таймауты/отмена Windows и
macOS должны быть проверены с размещённым API до коммерческого включения Online.

POST JSON:

```json
{"product":"duck-pocket","protocol":2,"key":"DUCK7K3M9X2P6R8N4W5T","device":"42 digits"}
```

Успех: HTTP 200, JSON `{"license":"DP2.…"}`. Клиент независимо проверяет
подпись и устройство; ответ `active=true` ничего не активирует.
Ошибка: HTTP 400/403/409/429/503, без PEM/подробностей внутренней базы.
Нельзя принимать непроверенное поле M и подписывать его: сервер сам строит M
из UUID оплаченной покупки и проверенного по форме device42.

Короткий ключ: `DUCK` + 16 случайных Crockford Base32 символов
(`0123456789ABCDEFGHJKMNPQRSTVWXYZ`), 80 бит энтропии.
В письме — дефисы, на сервере/клиенте — uppercase без дефисов/пробелов.
PHP `duckPocketShortKey()` создаёт ключ через CSPRNG random_int.
В базе хранить SHA256 канонического ключа, связанный с покупкой/UUID;
для повторной отправки письма нужен отдельно защищённый механизм хранения.
Не логировать полный ключ, лицензию, исходный ID или PEM.

Серверный сценарий:

1. Подтверждённая оплата Lava: проверить актуальную подлинность webhook,
   статус, товар, сумму и валюту на сервере. Redirect браузера не доказательство.
2. UNIQUE(provider, order_id): одна покупка/UUID/короткий ключ; retry идемпотентен.
3. Письмо содержит только короткий ключ, без готового offline-файла.
4. Activation endpoint проверяет продукт/protocol, hash ключа, оплаченный заказ,
   checksum устройства и выбранный владельцем лимит устройств.
5. Транзакция: запись устройства с UNIQUE(purchase_uuid,device), выпуск/выдача DP2.
   Повторный запрос того же устройства не расходует дополнительный слот.
6. Rate limiting, ограничение тела запроса, секрет PEM вне web root и репозитория.

Сайт Timeweb обрабатывает подтверждённые оплаты Lava и отправляет короткий
ключ по SMTP. Offline-файл выдаётся в личном кабинете по коду устройства
после проверки покупки. Лимит — три устройства на покупку; Online и Offline
используют одни записи устройств. Проверка verify не занимает новый слот.
Клиент принимает также алфавит старых ключей сайта (L/U), чтобы обновление
не заставляло перевыпускать уже выданные ключи.

## Проверка и отзыв при открытии

POST `https://rainlinemusic.su/api/v1/verify`:

```json
{"token":"DP2.…","device":"42 digits"}
```

Запрос общий для экземпляров одного загруженного модуля: одновременные
открытия объединяются; запросы из отдельных процессов/форматов независимы.
Проверка запускается также после импорта Offline. Пока идёт сеть, действующая
лицензия работает. Таймаут подключения 3 s, общий предел ожидания 5 s.
Ответ ограничен 8 KB; редиректы запрещены. При закрытии модуля worker отменяется
и присоединяется; проверка native отмены остаётся частью ручного DAW-чеклиста.

Однозначный отзыв: HTTP 200 или 403, boolean `valid=false`, `error="revoked"`,
совпадающие `license_id` (UUID из DP2), `device` и `token_hash`
(SHA256 точной строки DP2 без завершающего перевода строки).
Подтверждение восстановления: HTTP 200, boolean `valid=true` и те же три
совпадающих поля. Другие ответы, HTTP 429/5xx, обрыв/неполный JSON и отсутствие
связи не меняют состояние. Повторов по таймеру нет: следующая попытка только
при следующем открытии/импорте.

Отзыв сохраняет SHA256 токена в соседнем файле `license.revoked` и отключает
обработку всех экземпляров модуля. Токен остаётся на диске для последующей
проверки восстановления. Повторный импорт того же отозванного файла без
подтверждения сервера не снимает отметку. Новая успешная Online-активация
или совпадающее подтверждение verify снимают её. Устаревший ответ не применяется
после замены/повторной активации лицензии.

## Ограничения

Без доступного сервера ещё не полученный отзыв не обнаруживается: это
осознанное сохранение Offline-работы. Уже полученный отзыв сохраняется локально.
Подмена системного ID, удаление локальных файлов или модификация бинарника
может обойти защиту. Машинная привязка и проверка сервера не являются абсолютной
защитой. Offline должен выдаваться через сайт с записью устройства и общим
лимитом: файл, выпущенный вручную вне базы, не имеет серверной активации.
